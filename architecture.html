Servis Mimarisi — Departman / Bot tabanlı

Her departmanın kendi Jira/Confluence/Bitbucket bot kullanıcısı var. Bot → departman → SSH target / path / container politikası eşlemesi Bot Registry'de tutulur. Gerçek credentials (SSH key, API token) Secrets Vault'tadır. Task geldiğinde Task Router (orchestrator) bot'u tanıyıp task tipini okur, hangi worker'a ne bilgiyle gideceğini belirler.

2. Task tipi nasıl belirlenir?

Jira task'ı açılırken label veya custom field ile tip belirtilir. Task Router bunu okur. Label yoksa LLM gateway üzerinden task açıklaması sınıflandırılır (fallback).
Jira label / field Task tipi Ne yapar Kullanılan worker Gereksinim Human onayı
ai:code code Repo clone → kod yaz → test → commit → PR aç Coding Agent Sandbox veya SSH target (dept'e göre) PR seviyesinde (BB)
ai:test test Belirtilen path'te Docker ile test çalıştır, sonuçları Jira'ya yorum olarak yaz Test Agent SSH target zorunlu + workdir path Yok (raporlama)
ai:commit-only commit Sadece değişiklik yap + commit + push. Kod çalıştırmaz. Coding Agent (commit-only mode) Sandbox (hafif) Evet — PO/yetkili commit'i incelemeli
ai:pr-review review-help Açık PR'ı özetle, risk çıkar, değişiklikleri Jira'ya yorum olarak ekle. Kabul etmez. Review Assistant Okuma erişimi yeter Evet — yetkili PR'ı inceleyip kabul eder
ai:qna question Task context'inden cevap üret, Jira yorumuna yaz Q&A Assistant Vector + MCP read Yok

Task Router'a gelen/çıkan payload (event schema)

// Jira Automation → bus: task.assigned (ham)
{
  "issue_key": "BE-123",
  "assignee":  "ai-bot-be",
  "labels":    ["ai:test", "priority:high"],
  "summary":   "Nightly regression on staging",
  "description": "..."
}

// Task Router → bus: task.routed (zenginleştirilmiş)
{
  "issue_key":  "BE-123",
  "department": "backend",
  "bot_id":     "ai-bot-be",
  "task_type":  "test",
  "execution": {
    "mode":            "ssh",                        // sandbox | ssh | commit-only
    "ssh_target_ref":  "secrets://vault/backend/ssh_key",
    "ssh_host":        "runner-be-01:22",
    "workdir":         "/srv/app/backend",
    "container_policy":{"cleanup": true, "keep_image": false}
  },
  "atlassian_creds_ref": {
    "jira":       "secrets://vault/backend/jira_token",
    "bitbucket":  "secrets://vault/backend/bb_token",
    "confluence": "secrets://vault/backend/conf_token"
  },
  "repo":       "bitbucket.dc/backend/service-a",
  "needs_human_approval": false
}
Kritik: Worker'lara gerçek credentials gitmez, sadece secrets://... referansı gider. Worker o referansı Secrets Vault'a sync çağırarak kısa ömürlü token/SSH key çeker. Böylece event bus'ta / loglarda credential sızmaz.

Çünkü "Jira'dan task düştü, nereye gidecek?" sorusunun cevabı sabit değil. Tip/departman/execution mode'a göre değişir. Router olmasa, her worker aynı registry/vault lookup'ı kendi yapmak zorunda kalır — tekrar eden logic + tutarsızlık. Router tek noktadan classifier + enricher; worker'lar sadece "hazır payload geldi, yap" der.

6. Uçtan Uca Akış Örnekleri

A. QA departmanı — SSH'lı test (ai:test)

  1. Jira'da QA-45 task'ı açılır, assignee: ai-bot-qa, label: ai:test.
  2. Webhook → Jira Automation → task.assigned event'i bus'a.
  3. Task Router Bot Registry'den ai-bot-qa → qa departmanı, ssh_host=qa-runner-01:22, path=/opt/tests, policy={cleanup:true, keep_image:true} bilgisini çeker.
  4. Label ai:test → mode=ssh. Secrets Vault referansları eklenir. task.test.requested publish edilir.
  5. Test Agent subscribe alır → Secrets Vault'tan SSH key çeker → SSH Executor'ü sync çağırır: "runner-01'e bağlan, /opt/tests'e gir, docker compose run pytest" komutu.
  6. Çıktı stream'lenir, sonuçlar toplanır. Policy gereği container silinir, image kalır.
  7. Test Agent MCP ile Jira'ya yorum yazar (aracı ai-bot-qa). tests.passed publish eder.
  8. Notifier Slack'teki #qa kanalına mesaj düşürür.

B. Backend — sadece commit (ai:commit-only)

  1. Jira BE-77, label ai:commit-only, description: "Deprecated API kullanımlarını kaldır".
  2. Task Router → mode=commit-only, needs_human_approval=true.
  3. Coding Agent commit-only mode'da çalışır: Sandbox'ta repo clone, LLM ile değişiklikleri yapar, kod çalıştırmaz, sadece commit + push.
  4. commit.pushed event'i yayılır (flag: needs_human_approval=true).
  5. Human Approval Gate subscribe alır → Review Assistant'ı tetikler: diff özeti, risk analizi, test etkisi LLM ile çıkarılır.
  6. Notifier PO'ya Slack'te onay butonu ile mesaj gönderir ("Onayla / Reddet").
  7. PO onaylarsa → approval.granted → Coding Agent PR açar / merge eder. Reddederse commit geri alınır, Jira'ya yorum.

C. Frontend — PR review yardımı (ai:pr-review)

  1. Yetkili PR açar, Jira task'ına ai:pr-review label'ı atar ve ai-bot-fe'yi mentionlar.
  2. Task Router mode=read-only, execution yok. task.review.requested publish eder.
  3. Review Assistant subscribe alır → MCP ile PR diff + tartışmaları okur, Vector'dan benzer geçmiş PR'ları getirir.
  4. LLM ile özet + risk + öneri çıkarır → MCP ile Jira yoruma yazar (ai-bot-fe kullanıcısıyla). Kabul etmez.
  5. Yetkili yorumu okuyup PR'ı kendi kabul eder. Bu bir otomasyon değil, yardım.

D. Q&A — bus kullanılmaz

  1. Kullanıcı chat'ten sorar: "QA-45 ne durumda, son test log'u ne diyor?".
  2. Q&A Assistant request alır → Bot Registry'den default bot seçer → Vault'tan token çeker.
  3. LLM gw'ye prompt + tool listesi gönderir. LLM tool_use: mcp.jira.get_issue üretir.
  4. Sonuçları toparlar, LLM özetler, kullanıcıya cevap. Hiçbir event publish etmez.
